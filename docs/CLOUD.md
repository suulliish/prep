## Что где лежит
- `users/{uid}` — сохранение без истории ответов (строка JSON) и `updatedAt`.
- `users/{uid}/attempts/{ГГГГ-ММ}` — история ответов по месяцам (у документа Firestore предел 1 МБ).
- `users/{uid}/snapshots/*`, `users/{uid}/meta/snaps`, `users/{uid}/meta/clock` — снимки и восстановление (раздел «Снимки и восстановление» ниже).
- Конфликт двух устройств (`src/engine/sync.ts`, с 02.10.2026):
  - в облако ничего не пишется, пока не загружена облачная копия (раньше устройство, сохранившее что-то до загрузки —
    экран корабля, PIN командира на новом телефоне, — выглядело «новее» и затирало облако);
  - история ответов и поведение **объединяются** с обеих сторон, ответы не теряются никогда;
  - пустое устройство (ни ответа, ни диагностики, ни опыта) никогда не побеждает облако;
  - остальное сохранение — с той стороны, где `updatedAt` больше; три последние заменённые копии остаются в браузере
    (`razlom.save.v1.before-replace`, `.2`, `.3`), испорченное сохранение — в `razlom.save.v1.corrupt`.
- `users/{uid}/usage/{ГГГГ-ММ}` — поведение по дням (с 02.10.2026, `src/lib/track.svelte.ts`): активное время, заходы, ранние
  нажатия «дальше» по местам, каждый шаг урока (сколько был, сколько нужно на чтение, ранние нажатия, сворачивал ли),
  разборы ошибок, уходы на середине, итоги «Биткә түсіндір», голосовой ввод. Подробности шагов хранятся 120 дней, сводка дня — 400.
  При загрузке из облака по каждому дню берётся запись с большим активным временем.
- Google/Firebase Analytics **не** подключён и не будет: данные ребёнка не уходят третьим лицам, а своя запись видит учёбу
  (шаги, темы, ошибки), а не просто клики. Правила Firestore те же: `users/{uid}/**` видит только сам вошедший.

## Правила Firestore (Firestore Database → Rules → вставить → Publish)
Каждый вошедший видит и меняет только свои данные.

```
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /users/{uid}/{document=**} {
      allow read, write: if request.auth != null && request.auth.uid == uid;
    }
    match /{document=**} {
      allow read, write: if false;
    }
  }
}
```

## Снимки и восстановление (S4, с 05.10.2026)
Код: `src/engine/snapshots.ts` (чистая логика, тесты `tests/snapshots.test.ts`), обвязка Firestore — `src/lib/cloud.svelte.ts`
(`snapshotStep`, `restoreSnapshot`, `inspectSnapshot`, `loadSnaps`; тесты с подменой Firebase `tests/cloud_snapshots.test.ts`), экран —
Командир → «Данные» → «Снимки облака» (`src/screens/commander/Snapshots.svelte`, вкладка уже за PIN).

- **Что лежит в облаке.** `users/{uid}/snapshots/{ГГГГ-ММ-ДД}` — главный документ облака (сохранение без истории ответов, та же схема, что
  `users/{uid}`, строка JSON) в том виде, каким он был ПЕРЕД первой записью этих суток, плюс `at`, `app`, `v`, `sum`. `users/{uid}/snapshots/before-restore-{мс}` —
  копия «до», делается перед каждым восстановлением. `users/{uid}/meta/snaps` — список снимков со сводкой (`{index: {id: {at, app, v, kind, sum}}}`):
  экран листает его, не скачивая сами снимки. `users/{uid}/meta/clock` — отметка времени сервера (см. ниже). Правила Firestore те же (`users/{uid}/**`).
- **Когда снимается.** После успешной записи в облако (`push`), не чаще раза в час за сеанс, и только если: устройство уже прочитало облако (`pulled`),
  схема облака не новее приложения (`readOnly` нет), за эти серверные сутки снимка ещё нет, облако не пустое, документ ≤ 950 000 знаков.
  Снимок пишется в одной транзакции со списком и чисткой. Сбой снимка не мешает синхронизации.
- **Сутки — по серверу, не по часам телефона.** Время берётся так: в `meta/clock` пишется `serverTimestamp()` и читается обратно; сутки Казахстана (UTC+5).
  Нет ответа сервера — снимка нет. Поэтому телефон с датой 2031 года не создаст снимок «из будущего» и не удалит настоящие.
- **Срок.** Снимки дня — 14 дней (на 15-й удаляется при записи нового); три самых свежих остаются всегда, даже старые (если приложение не открывали три недели).
  Копии «до восстановления» — 60 дней.
- **Восстановление.** Список (дата, ответов по темам, тем, монет) → «Сравнить» (сейчас → в снимке по 5 показателям, предупреждение, если снимок «меньше») →
  «Восстановить…» → предупреждение и вторая кнопка «Да, восстановить». Порядок внутри `restoreSnapshot`: свежая загрузка облака (`pull`) → проверка снимка →
  копия «до» в облаке (не записалась — стоп, ничего не изменено) → `replaceSave` (прежнее сохранение ещё и в трёх локальных копиях `.before-replace`) →
  немедленная обычная синхронизация (транзакция с `rev`). Откат — тот же путь: восстановить копию «до восстановления» из списка.
- **Что не теряется.** Ответы (в снимке их нет; остаются ответы устройства и облака, `mergeAttempts`), поведение по дням, вопросы к ИИ-помощнику, PIN командира
  (остаётся тот, что на устройстве). Всё остальное (опыт, монеты, темы, дни, настройки…) становится как в снимке.
- **Что не восстанавливается.** Снимок более новой схемы (`v` или `version` > `CLIENT_SCHEMA`), повреждённый (не JSON, странные типы), пустой (без прогресса).
  Пока облако новее приложения (`readOnly`), восстановление запрещено. Во время урока/задания у ребёнка — тоже.
- **Известное ограничение (важно).** Восстановление идёт через обычную синхронизацию. Слияние устройств устроено так, что «только растущее» (опыт — максимум,
  дни и открытое — объединение, тема с большим числом ответов побеждает) берётся с того устройства, где этого больше. Поэтому, если на ДРУГОМ устройстве
  прогресс новее снимка, оно при синхронизации вернёт эти части обратно, и восстановление частично отменится. Проверено запуском на двух устройствах: опыт, темы и дни вернутся, а монеты и план дня останутся из снимка (монеты, заработанные после снимка, пропадут навсегда, пока не откатить копией «до»; откат проверен, возвращает всё). Надёжное решение — «эпоха» восстановления
  (поле `epoch` в главном документе: устройство со старой эпохой заменяет своё, а не сливает, как в спецификации data.md); сделано не было, нужно отдельно, вместе с правилами (S3).
- **Правила Firestore (S3).** Когда будут опубликованы ужесточённые правила, они должны разрешать владельцу: создание `snapshots/*`, запись `meta/snaps` и `meta/clock`,
  удаление `snapshots/*` старше 14 дней (копии «до» — старше 60). Главный документ снимки не трогают (`rev` не меняется).
- **Не проверено на настоящем Firebase.** Все проверки — на подменённом Firestore (в т. ч. что serverTimestamp читается обратно сразу после записи).

## Офлайн-кэш (S7, с 05.10.2026)
Код: шаблон `scripts/sw.template.js` + сборка `scripts/swbuild.mjs` (подставляет версию сборки `APP_VERSION` и хэши файлов голоса/моделей, получается `dist/sw.js`;
файла `public/sw.js` больше нет), регистрация — `src/main.ts` (только на настоящем сайте), тесты — `tests/sw_cache.test.ts` (настоящий шаблон, подменены `caches`/`fetch`).

- **Три кэша** (имена на `zharyq`, чужие кэши на домене не трогаются): `zharyq-shell-<сборка>` — страница и файлы `assets/` (хэш в имени); остаются
  текущая и предыдущая сборка, остальные удаляются при активации новой версии. `zharyq-media` — голос, модели, звуки, картинки из `public/`.
  `zharyq-meta` — какие сборки хранятся.
- **Голос и модели с хэшем.** Каждый файл хранится под ключом «адрес?h=<хэш содержимого>»; список хэшей зашит в `sw.js`. Файл изменился — старая копия не находится
  и при активации удаляется; неизменённые остаются (60 МБ заново не качаются). В кэш попадают только файлы из списка сборки, поэтому размер не может вырасти больше самих файлов сайта.
- **Аудио-элемент просит куски (Range).** Раньше такой ответ (206) в кэш не клался вовсе — офлайн-голос не работал. Теперь файл качается целиком, кладётся в кэш, а
  запрос получает правильный кусок 206 (так нужно Safari).
- **Страница** — сначала сеть (обновления), без сети — копия, потом корень сайта; `sw.js` и `version.json` всегда из сети; в кэш только ответы 200.
- **Переход со старого кэша.** Прежний `zharyq-v1` доживает одну смену версии (открытая страница может ещё просить из него куски), потом удаляется.
  Голос из него в новый кэш не переносится (хэш неизвестен): после обновления он один раз скачивается заново, по мере того как Бит его произносит.
- **Что осталось.** Предзагрузки голоса нет (как и раньше: офлайн работает то, что уже слышали при интернете). Перезагрузка открытой страницы после новой версии
  и ошибка загрузки куска сборки (`App.svelte`) — отдельная задача (D6/S6).
